# 卒研: way 138533178 の一方通行判定 原因切り分け調査

## 背景・現状

渋谷→新宿ルートにおいて、システムが `way 138533178` を「一方通行の逆走（oneway違反）」として検出していた。この事例は中間発表ポスターおよび検証結果（R2: Googleルート比較、oneway違反18件）の代表例として扱っていた。

しかし **Googleストリートビューで現地を確認したところ、当該区間の一方通行標識には「自転車を除く」の補助標識が付いていた**ことが判明した。つまり自転車にとっては逆走ではなく、合法的に通行可能である。

システムの判定ロジックでは `oneway:bicycle=no` 等の自転車除外タグは違反としない設計になっているため、以下2つの可能性がある。

- **仮説A（OSMデータ不備）**: 実験に使用したOSMデータに `oneway:bicycle=no` が付与されておらず、システムは仕様通り正常に動作した。原因はOSMのタグ品質。
- **仮説B（システムのバグ）**: OSMデータには自転車除外タグが存在していたが、システムがそれを読み取れず違反と誤判定した。

**この調査の目的は、A と B のどちらかを事実に基づいて確定させることである。** 修正作業はこの切り分けが終わるまで行わない。

---

## 重要な前提

- **既存の実験データ・ground_truth.csv・google_comparison.csv を書き換えないこと。** 本タスクは調査のみ。
- 調査結果は新規ファイル `backend/data/investigation_138533178.md` に記録する。
- 判断や解釈を先回りせず、取得した生データをそのまま提示すること。

---

## Step 1: 現在のOSMタグを取得

Overpass API で way 138533178 の全タグを取得する。

```
[out:json][timeout:25];
way(138533178);
out tags meta;
```

**記録すべき項目:**

- 全タグのkey-valueペア（省略せず全件）
- 特に以下のキーの有無と値:
  - `oneway`
  - `oneway:bicycle`
  - `bicycle`
  - `bicycle:backward` / `bicycle:forward`
  - `cycleway` / `cycleway:left` / `cycleway:right`
  - `traffic_sign` / `traffic_sign:backward`
  - `highway`
- `version` / `timestamp` / `changeset`（metaに含まれる。編集時点の特定に使う）

---

## Step 2: 実験時点のOSMデータからタグを直接抽出

**これが最も重要なステップ。** Overpassが返すのは「現在」のタグであり、実験に使用したデータとは異なる可能性がある。

使用したOSMデータファイル（`kanto-latest.osm.pbf`）から直接抽出する。

```bash
# osmium-tool が未インストールなら導入
# apt install osmium-tool  または  brew install osmium-tool

osmium getid -t <pbfへのパス>/kanto-latest.osm.pbf w138533178 -f opl
```

`-f opl` が読みにくい場合は `-f xml` でも可。

**記録すべき項目:**

- 抽出された全タグ
- pbfファイルのタイムスタンプ（`ls -l` および `osmium fileinfo <pbf>` の出力）
- Step 1 で取得した現在のタグとの差分

**osmium が使えない場合の代替:**
GraphHopper が生成したグラフキャッシュ、またはプロジェクト内で pbf を読んでいる既存コード（`services/` 配下）を利用して該当wayのタグをダンプする方法を検討し、実施した手段を記録すること。

---

## Step 3: OSM編集履歴の確認

way 138533178 の編集履歴を確認し、`oneway:bicycle` 等の自転車関連タグがいつ追加されたか（あるいは一度も追加されていないか）を特定する。

```
https://www.openstreetmap.org/api/0.6/way/138533178/history.json
```

**記録すべき項目:**

- 各バージョンの timestamp と、そのバージョンにおける oneway 関連タグの状態
- pbfのタイムスタンプ（Step 2）との前後関係

---

## Step 4: システムのタグ解釈ロジックの単体確認

**Step 2 で pbf 側に自転車除外タグが存在した場合のみ実施。** 存在しなかった場合は仮説Aが確定するのでスキップしてよい。

`services/law_checker.py` の oneway 判定関数に対し、以下のタグセットを持つ疑似エッジを入力して挙動を確認する。

| ケース | タグ | 期待される判定 |
|---|---|---|
| 1 | `oneway=yes` のみ、逆走方向 | 違反 |
| 2 | `oneway=yes` + `oneway:bicycle=no`、逆走方向 | 違反としない |
| 3 | `oneway=yes` + `cycleway=opposite`、逆走方向 | 違反としない |
| 4 | `oneway=yes` のみ、順走方向 | 違反としない |

**記録すべき項目:**

- 各ケースの実際の出力
- 期待と異なった場合、`law_checker.py` の該当行番号とロジックの内容

---

## Step 5: 他の17件への波及確認（調査のみ）

`backend/data/google_comparison.csv` から oneway違反として検出された全18件のway IDを抽出し、リスト化する。

各way IDについて Step 1 と同じ方法で現在のOSMタグを取得し、以下の表形式で `investigation_138533178.md` に出力する。

| way_id | oneway | oneway:bicycle | bicycle | cycleway | highway | 備考 |
|---|---|---|---|---|---|---|

**この段階では判定の正誤を結論づけないこと。** 現地確認（ストリートビュー）はユーザーが手動で行うため、Claude Code はタグの一覧化までを担当する。
