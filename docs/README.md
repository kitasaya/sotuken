# 卒研文書の配置ルール

このファイルは、新しい作業セッションが文書を探し、追加先を判断するための入口である。分類軸は文書の主題ではなく、**今後どのように維持するか（寿命）**とする。

## 1. 最初に読む順序

1. `docs/README.md`（本ファイル：配置と更新規則）
2. `RESEARCH.md`（研究の現在地）
3. `docs/台帳/数値台帳.md`（数値の唯一の正）
4. `docs/検証記録/検証記録_18点.md`（旧18点の画像確認済み一次記録）
5. `docs/分析/分析_18件内訳.md`（旧18点の全数内訳）
6. `docs/構成/主張構成案.md`（論文の主張構成）
7. `docs/台帳/未確定事項リスト.md`（現時点で言えないこと）
8. `docs/台帳/撤回台帳.md`（復活させてはいけない主張）
9. `docs/台帳/要判断リスト.md`（判断保留事項）

## 2. フォルダの役割

| 場所 | 寿命 | 置く条件 |
|---|---|---|
| `RESEARCH.md` | Living | 研究全体の現在地。過去値を併存させない |
| `docs/台帳/` | Living / Append-only | 数値、未確定事項、判断、撤回など、研究全体で継続管理する記録。`撤回台帳.md` は追記のみ |
| `docs/構成/` | Living | 論文の主張・章立てなど、今後も更新する構成文書 |
| `docs/文献/精読ノート/` | Append-only | 本文を読んで確認した文献ごとの精読記録 |
| `docs/文献/調査/` | One-shot | 特定テーマの文献探索結果 |
| `docs/文献/書誌/` | Append-only / One-shot | 書誌確認、取得確認、書誌カード |
| `docs/分析/` | One-shot | 特定時点の分析、実装確認、統計確認。原則として後から現在値へ上書きしない |
| `docs/検証記録/` | Append-only | 人の確認を伴う検証記録と、その記入用テンプレート |
| `docs/指示書/` | Archive | 過去作業の指示書。実施後も履歴として保持する |
| `docs/アーカイブ/適用済み/` | Archive | 適用済み改訂指示・監査 |
| `docs/アーカイブ/旧二重管理/` | Archive | 正ではなくなった凍結コピー。編集・現行値参照は禁止 |
| `bicycle-navi/` | System / raw evidence | 実装、分析スクリプト、生データ、実行結果。文書整理だけを理由に移動しない |

### アンケート回答データ

- 設問票・説明文・記入テンプレートは、人の確認手順として `docs/検証記録/` に置く。
- 実施後の**匿名化済み回答データ**と集計用の生データは `bicycle-navi/backend/data/survey/` に置く。分析結果をMarkdownでまとめる場合は `docs/分析/` に置き、回答データを複製しない。
- 氏名、メールアドレス、学籍番号、自由記述中の個人識別情報などを含む元回答は、**Git管理下に置かない**。リポジトリ外のアクセス制御された保管先に保存し、匿名化・対応表の分離後に必要最小限のデータだけを上記フォルダへ入れる。
- やむを得ず作業ツリー内で一時処理する場合は、先に専用パスを `.gitignore` へ追加し、`git status` で追跡対象外であることを確認する。個人情報をコミット履歴から後で消す運用を前提にしない。

### PDFの例外

`先行研究精読ノート/取得PDF/` の14 PDFは `.gitignore` の `*.pdf` によりGit管理外だった。履歴を保つ `git mv` が使えず、生データを削除・改変しない規則を優先して、バッチ12では元の場所に残した。**Git管理下にあるという当初前提と実リポジトリの状態が一致しなかったための例外**である。追跡方法を決めるまでは移動・改名しない。

## 3. 新規ファイルの判断フロー

1. 実装・生データ・実行結果か？
   - はい → 既存の `bicycle-navi/` の責務に従う。アンケートの匿名化済み回答は `bicycle-navi/backend/data/survey/`。卒研文書側へ複製しない。
   - いいえ → 2へ。
2. 今後も現在値へ更新するか？
   - 数値・未確定・判断・撤回を管理する → `docs/台帳/`
   - 論文の主張や章構成を更新する → `docs/構成/`
   - いいえ → 3へ。
3. 過去の個別記録を残しながら追記するか？
   - 文献本文の確認記録 → `docs/文献/精読ノート/`
   - 人による検証記録 → `docs/検証記録/`
   - いいえ → 4へ。
4. 特定時点だけの分析・調査か？
   - 研究データの分析 → `docs/分析/`
   - 文献探索・書誌確認 → `docs/文献/調査/` または `docs/文献/書誌/`
   - いいえ（作業指示・適用済み資料）→ `docs/指示書/` または `docs/アーカイブ/`

迷った場合は、将来のエージェントが「更新すべき正」と誤認する危険が低い場所を選び、`docs/台帳/要判断リスト.md` に判断理由を残す。

## 4. 新規ファイルの命名規則

- 既存ファイルはリンク保全のため原則改名しない。以下は新規ファイルだけに適用する。
- 一時的な連番や `final`、`最新版` を使わず、内容が分かる日本語名にする。
- 単発分析は `分析_<対象>.md`、検証記録は `検証記録_<対象>.md`、精読ノートは `精読ノート_<著者等><年>.md` とする。
- 日付が分析条件として必要な場合だけ `YYYY-MM-DD` を含め、本文冒頭にも基準時点を書く。
- 同じ正を別形式で手編集しない。表形式の派生物が必要なら、正から再生成できる方法と生成元を明記する。

## 5. やってはいけないこと

- `docs/台帳/数値台帳.md` 以外に、競合する「数値の正」を作らない。
- 同じ内容を `.md` と `.csv` で二重に手編集しない。
- `docs/台帳/撤回台帳.md` の値や主張を現行文書へ復活させない。
- 確認済み事実と幾何的診断・推測を混同しない。推測には `【推測】` を付ける。
- 生データ（CSV、JSON、PDF、実行ログ）を削除・改変しない。
- 文書整理を理由に判定ロジックを変更しない。
- Git管理下のファイルを通常の移動で移さない。必ず `git mv` を使う。
- リンク確認なしで移動を完了扱いにしない。

## 6. 二重管理の方針

### 旧18点の検証記録

`docs/検証記録/検証記録_18点.md` を唯一の正とする。人が画像撮影年月・標識内容・判定を編集するためである。旧CSVは生データ削除禁止に従って `docs/アーカイブ/旧二重管理/検証記録_18点.csv` へ `git mv` し、**バッチ11反映前の凍結資料**として保持する。現行値の参照や手編集は禁止する。

現時点ではCSVを使う処理がないため、生成スクリプトは作らない。将来CSVが必要になった場合は、Markdownを入力として再生成できるスクリプトを追加し、CSVを正にしない。

### `known_violations.py` の旧分類

`bicycle-navi/backend/scripts/known_violations.py` は、過去の検証スクリプトを再現するため意図的に当時の分類を保持している。現行分類との二重管理に見えるが、現行値の正ではなく**歴史的な実行入力**である。卒論スコープでは構造を変更せず、docstringの警告と現行文書への参照で管理する。

### その他の確認結果

同一内容の別形式とGit管理下ファイルの完全一致ハッシュを機械的に探索した結果、上記以外に、現行値を人が二重編集する同種の組合せは確認されなかった。完全一致は空のPythonパッケージ初期化ファイル（`backend/routers/__init__.py`、`backend/services/__init__.py`）だけで、研究記録の二重管理ではない。`bicycle-navi/backend/data/` のCSV・JSONとMarkdown中の集計表は、前者が生データ／実行結果、後者が説明または台帳への出典付き転記であり、正の役割を分離する。
