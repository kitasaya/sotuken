# 分析：有用性の根拠（R1に違反が残っていないかの確認）

**分析日：2026-08-28（バッチ14） ／ 基準：GraphHopper 11.0・`kanto-260801.osm.pbf`・Overpass attic `2026-08-01T20:21:21Z` 固定**

研究室内中間報告（9月中旬）で提示する中心主張

> Google Maps のルートには実際に交通違反が存在し、本システムはそれを回避できる。

のうち、**後半「回避できる」の測定状況**を確認した記録である。前半「違反が存在する」は真の違反3way・4点のストリートビュー目視確認で既に示せている（`docs/検証記録/検証記録_18点.md` P10/P12/P13/P18）。

**⚠️ 本主張の対象は一方通行違反に限られる。** Layer 2（二段階右折）は案内のみで経路除外を行っていない（`bicycle-navi/backend/services/route_analyzer.py:263`）。発表では「回避できる」の射程を一方通行に限定して述べること。

## 1. なぜ14/15ペアが「測定済み」と言えるのか

### 1.1 コードを読んで確認した事実

`analyze_route(v3)` は法規判定を**初期ルート（リルート前）に対してのみ**実行し、リルート後の準拠ルートを再判定しない。`_build_response` の中に `check_*` の呼び出しは存在しない。

- 出典：`bicycle-navi/backend/services/route_analyzer.py:193-197`（判定の入力はすべて初期ルート由来）、同 `:256-307`（`_build_response` に再判定なし）
- 先行確認：`bicycle-navi/backend/data/investigation_r1_material.md` §1.2・§3.1（2026-07-30、同じ結論）

したがって `google_comparison.csv` の `system_violation_count`（合計11件）は**リルート前の違反数**であり、そのままでは「R1に残る違反」ではない。

### 1.2 ただし14ペアでは初期ルート＝R1である

`_build_response` は、oneway 違反が1件もないペアでは分岐に入らず、`compliant_route = original_route`（**同一オブジェクト**）を返す（`route_analyzer.py:263, 275-276`）。

`rerouted=False` のペアでは、判定対象の初期ルートと、最終的に利用者へ提示されるルートが**同一経路**である。よって既存の判定結果がそのままR1の判定結果になる。

15ペア中 `rerouted=True` は横浜→みなとみらいの1ペアのみである（`bicycle-navi/backend/data/verify_v2_analyze_route.csv` 2–16行の `rerouted` 列）。

### 1.3 測定済み14ペアの一方通行違反数

`verify_v2_analyze_route.csv` の `violation_types` 列に `oneway` が現れるのは14行（横浜→みなとみらい）だけである。他の14ペアはすべて空欄または `two_step_turn` である。

`ground_truth_template.csv` の `detected_rule` 列でも、`oneway` の行は16行目（横浜→みなとみらい、way 28413951）の1行のみである。

### 1.4 未測定の1ペア（横浜→みなとみらい）

- 初期ルート 2,277.7m に一方通行違反1件（way 28413951、県道80号・横浜駅根岸線、`oneway=yes; highway=primary`、confidence 1.0）
- これを `custom_model` の `areas` でブロックして準拠ルート 2,697.6m を生成（+419.9m）
- **この準拠ルート2,697.6mは一度も採点されていない**

算出可能性を確認した結果：

| 必要なもの | 状況 |
|---|---|
| 準拠ルートのジオメトリ | **保存されていない。** `compliant_route` は API レスポンスにのみ存在し、CSVには距離・時間しか残っていない。リルート発生時は `compliant_route.details` も空（rerouter が `details` を要求しないため。`rerouter.py:80-87`） |
| 再取得の手段 | GraphHopper（Docker）を起動して `POST /route` を再実行する必要がある |
| 実行可否 | **本作業時点では不可。** Docker デーモンが停止しており `localhost:8989` に接続できない。PBF（`bicycle-navi/graphhopper/kanto-260801.osm.pbf`）とグラフキャッシュ（`default-gh/`）は残存しているため、Docker 起動と8/1固定Overpass attic の再取得ができれば技術的には測定可能である |

**したがって「既存の生成済みデータからは算出できない」が結論である。**

### 1.5 幾何的に言えること（測定の代用にはしない）

リルートのブロック矩形は違反座標を中心とする ±0.001度の正方形である（`rerouter.py:10-19`）。横浜→みなとみらいの違反座標 (35.464037, 139.623297) から、ブロック矩形は

- 緯度 [35.463037, 35.465037]、経度 [139.622297, 139.624297]

となる。**この矩形は、同ペアのGoogleルート側で検出された真の違反2点（P12: 35.46414/139.62264、P13: 35.46358/139.62261、いずれも way 28413948）を内側に含む。** 当該エリアの priority は `multiply_by: "0"` で完全ブロックされるため、準拠ルートがこの2点の区間を通ることはない。

**⚠️ これは幾何的な包含関係の計算であり、準拠ルートの採点ではない。** 準拠ルートが**別の場所**で新たな一方通行違反を含む可能性は、この計算では排除できない。発表では「未測定である」と述べ、この包含関係を測定結果として提示しないこと。

## 3. この結果を主張として使うときの限定条件【重要】

### 3.1 R1とR2は判定関数を共有するが、wayの特定方法が異なる

`external_route_scorer.py` は `law_checker` の `check_oneway_violation` を**そのまま再利用**しており、判定基準そのものは同一である（同ファイル docstring、`RESEARCH.md` 13.2節）。しかし、その手前の **way の特定方法は非対称**である。

| 項目 | R1（本システム） | R2（Googleルート採点） |
|---|---|---|
| wayの特定 | GraphHopper の `osm_way_id` path detail（実際に通過したwayのID） | 40m等間隔サンプリング＋最近傍way探索（`get_bulk_way_data`） |
| 座標マッチングの介在 | **なし** | **あり** |
| B群（分離wayの対向車線誤選択）の発生余地 | **原理的にない** | **ある** |

出典：`RESEARCH.md` 13.2節「検出条件の非対称（既知の限界・論文に明記すること）」、`route_analyzer.py:108-157`、`external_route_scorer.py:174-196`。

**含意：** 「R1が0件、R2が12点」という差は、法規準拠性の差と、way特定方法の差の**両方**を含む。R2の12点のうち8点（A群4点・B群4点）は誤検出であり、そのうちB群4点はR1側では原理的に発生しない種類の誤りである。したがって **12対0という数字をそのまま「本システムの方が12件分法規準拠である」と読ませてはならない。**

**正しい比較対象は、R2の12点のうち真の違反3way・4点である。** この4点はway特定の誤りではなく実在の一方通行違反であり、これらを含まない経路を提示できることが本システムの主張になる。

### 3.2 真の違反4点が属するペアでのR1の状況

真の違反4点は3ペアに分布する。

| 真の違反 | way | ペア | 当該ペアのR1 | R1の一方通行違反 |
|---|---:|---|---|---|
| P10 | 853388885 | 立川→国分寺 | 初期ルート＝R1（rerouted=False） | **0件（測定済み）** |
| P12・P13 | 28413948 | 横浜→みなとみらい | 準拠ルート（rerouted=True） | **未測定**（ブロック矩形は当該2点を含む。§1.5） |
| P18 | 151808609 | 千葉→幕張本郷 | 初期ルート＝R1（rerouted=False） | **0件（測定済み）** |

出典：`docs/検証記録/検証記録_18点.md` P10/P12/P13/P18、`docs/分析/分析_現行12点マージン分布.md`、`verify_v2_analyze_route.csv` 13,14,16行。

**発表で言えること：** Googleのルートが真の一方通行違反を含んだ3ペアのうち、2ペアでは本システムのルートに一方通行違反が0件であることを同じ判定関数で測定した。残る1ペアは未測定である。

**発表で言えないこと：** 「真の違反4点をすべて回避した」と断定すること。横浜→みなとみらいは未測定である。

### 3.3 Layer 1（経路除外）が作動したのは1ペアのみで、そのwayの真偽は未検証

15ペアの実験で `custom_model` による経路除外が実際に作動したのは横浜→みなとみらいの1ペアだけである。そのとき除外されたwayは **28413951**（県道80号・横浜駅根岸線）であり、

- ストリートビューによる目視確認の18点母集団には**含まれていない**
- `ground_truth_template.csv` 16行の `true_oneway_violation` 列は**空欄（人手判定待ち）**

したがって、**この1件が真の違反だったのか誤検出だったのかは未検証である。** 誤検出であれば、+419.9m の迂回は不要なコストだったことになる。

これは `docs/台帳/未確定事項リスト.md` の E-9（現地基準R1のPrecision・Recall・F1が未確定）に含まれる既知の未確定事項である。**発表では、Layer 1の作動実績が n=1 であり、その真偽が未検証であることを隠さずに述べること。**

### 3.4 判定に使うOSMタグは経路生成にも使われている

初期ルートは GraphHopper の `bike` プロファイル（`bike_access` ベース）で生成され、判定も同じOSMの `oneway` タグを見る。したがって「初期ルートの段階で一方通行違反が15ペア中1件しか出なかった」ことは、Layer 1 の効果ではなく、**経路探索器が最初から `oneway` を概ね尊重していること**による可能性がある。

出典：`bicycle-navi/graphhopper/config.yml`（`bike` プロファイルの custom_model は `!bike_access` のみ）、`investigation_r1_material.md` §3.3「oneway が1件しかないのはリルートで消えたからではなく、初期ルートの段階でそもそも1件しか検出されていない」。

**【推測】** GraphHopper の `bike_access` が方向別に評価されるため、一方通行の逆走エッジが初期ルートに入りにくいことが、1件しか出なかった理由と考えられる。ただし本研究では GraphHopper の内部挙動を検証していないため、**推測にとどめ、発表では断定しない。**

## 4. A-3：回避のコストの整理

### 4.1 確定した数値と出典

| 項目 | 現在値 | 出典 |
|---|---:|---|
| 距離差 ±0m のペア | **14/15ペア** | `bicycle-navi/backend/data/verify_v2_analyze_route.csv` の `new_distance_diff_m` 列が `0.0` である14行（2–13, 15, 16行）。`docs/台帳/数値台帳.md` §4「距離差0：14/15ペア」 |
| 距離が増えたペア | **1/15ペア**（横浜→みなとみらい） | 同CSV 14行。`rerouted=True` |
| 当該ペアの初期距離 | **2,277.7m** | 同CSV 14行 `new_original_distance_m`。`docs/台帳/数値台帳.md` §4「初期距離 2,277.7m」 |
| 当該ペアの準拠距離 | **2,697.6m** | 同CSV 14行 `new_distance_m`。`docs/台帳/数値台帳.md` §4「準拠距離 2,697.6m」 |
| 距離増 | **+419.9m（+18.4%）** | 同CSV 14行 `new_distance_diff_m`。増加率は `419.9 / 2,277.7`。`docs/台帳/数値台帳.md` §4 |

### 4.2 発表で使う表現（「平均+18.4%」と誤読されない書き方）

**推奨する言い方：**

> 15ペア中14ペアでは、法規準拠ルートと最短ルートの距離差は **±0m** だった。距離が増えたのは横浜→みなとみらいの **1ペアだけ**で、2,277.7m から 2,697.6m へ **+419.9m** 増えた。この **+18.4%** は、**その1ペアの初期距離2,277.7mに対する比**であり、15ペアの平均ではない。

**スライドに載せる表現（案）：**

| 距離コスト | 値 |
|---|---|
| 距離差±0mのペア | 14/15 |
| 距離が増えたペア | 1/15（横浜→みなとみらい） |
| その1ペアの増加 | +419.9m（2,277.7m → 2,697.6m） |

**書いてはいけない表現：**

- 「平均 +18.4%」「平均的に約18%の迂回」（1ペアの値であり平均ではない）
- 「+18.4% の迂回コストで法規準拠を実現」（15ペア全体の話に読める）
- 「ゼロコスト」「迂回 0/15」「+0.0m」（`docs/台帳/撤回台帳.md` で撤回済み。全15ペアで距離増0mは固定条件で再現しない）
- 「%」だけを単独で書く（必ず m と分母の初期距離2,277.7mを併記する）

### 4.3 コストの解釈

違反を含まないペアでは追加距離が生じず、実在の一方通行エッジを避けるペアでのみ迂回が生じるという分布である（`RESEARCH.md` 14.3節）。

**ただし §3.3 の限定が付く。** 唯一の迂回事例（way 28413951）の真偽が未検証であるため、「+419.9m は真の違反を避けるために必要だったコストである」とは現時点では言えない。発表では「実在の `oneway=yes` エッジを避けた結果の迂回である」までとし、真の違反であることを前提にした表現は避ける。

## 5. 発表での主張の書き方（確定案）

**使ってよい形：**

> Google Maps のルートを本システムと同じ判定関数で採点した結果、15ペア中10ペアで違反エッジを検出し、そのうちストリートビューによる目視確認で真の一方通行違反と確定したものが3way・4点あった。一方、本システムが提示するルートについては、15ペア中14ペアで一方通行違反が0件であることを同じ判定関数で測定した。残る1ペアは、リルート後のルートを再判定する仕組みが未実装のため未測定である。距離コストは14/15ペアで±0m、迂回が生じた1ペアで+419.9mだった。

**使ってはいけない形：**

- 「本システムのルートには違反が一切ない」（15ペア中14ペアの測定であり、かつタグ基準の測定である）
- 「本システムは違反を完全に排除する」（未測定1ペアがあり、Layer 2は排除していない）
- 「二段階右折も回避する」（案内のみ。経路除外の対象外）
- 「12件の違反を回避した」（R2の12点には誤検出8点が含まれる。真の違反は4点）
