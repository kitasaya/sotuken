# 分析：除外機構の実証（バッチ21）

**実施日：2026-08-30 ／ 固定PBF：`kanto-260801.osm.pbf` ／ GraphHopper：11.0**

## 1. 結論

判定は **(イ) 条件Bでも違反が出ない** である。

GraphHopper標準bikeルート（条件B）を15ペアすべて同じ判定器で採点した結果、一方通行違反は0/15ペアだった。条件Bで違反がなかったため、現行方式（条件A）のrequest-scoped `custom_model areas`は全ペアで未発動となり、A/Bのルートgeometryと距離は15/15ペアで完全に一致した。

したがって、この15ペアからはcustom_model除外機構の寄与を実証できない。実装可能性は回帰テストで示せるが、実路線でGraphHopper標準bikeルートより違反を減らしたという有用性の実績は0件である。

## 2. 比較条件

| 条件 | 実装上の定義 |
|---|---|
| A：custom_modelあり（現行方式） | 条件Bを同じ判定器で採点し、oneway違反があった場合だけ`rerouter.py`と同じ約100mの`areas`・`multiply_by=0`を付けて再生成する |
| B：GraphHopper標準bike | `GET /route?profile=bike`。request bodyに追加の`custom_model areas`を渡さない |

GraphHopperの保存済み`bike`プロファイル自体は、`bike_access`と`bike_average_speed`を使う設定である。ここで無効化したのはLayer 1が追加する**リクエスト単位の除外エリア**であり、bikeプロファイルの基本的な通行可否・速度設定ではない。基本設定まで除去すると「標準自転車プロファイル」と同じ比較にならないためである。

## 4. 横浜→みなとみらいの切り分け

- 条件Bはway 28413948を通らなかった。
- 条件Bは閉ループway 28413951を通ったが、修正後判定は順方向だった。
- 保存済みGoogle polylineはway 28413948上のP12・P13で逆方向走行として検出されている。
- したがって、Googleルートと本システムルートの差は、custom_modelが28413948を検出後に排除した結果ではない。GraphHopper標準bikeプロファイルが最初から別経路を返している。

P12・P13が真の違反であることはR2の人手確認結果として維持されるが、それをLayer 1の除外実績へ読み替えてはならない。

## 5. 距離と有用性の解釈

条件A/Bの距離差は15/15ペアで0.0mだった。ただし、これは「法規準拠がゼロコストだった」という実証ではない。条件Bで違反が0件だったため、除外制約が一度も投入されなかった結果である。

本研究で現在言えることは次の範囲に限る。

1. 閉ループ順走・逆走の合成回帰テストにより、違反座標をcustom_model areasでブロックする機構を実装できる。
2. 今回の15ペアではGraphHopper標準bikeルートがすでにoneway違反0件であり、追加除外の実地寄与は観測できなかった。
3. custom_modelの有用性を実証するには、標準bikeプロファイルがOSM上のonewayを逆走する再現可能な実例、または標準プロファイルでは表現できない追加規則を対象に、制約あり／なしを比較する必要がある。
