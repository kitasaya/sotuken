## 2. 問題点【必須】（1枚）

### 話す内容

> **既存のナビゲーションシステムは、交通法規違反を含む経路を生成しうる。違反を経路生成の段階で事前に排除する仕組みが必要である。**

- 自転車ナビゲーションの多くは自動車用のノードマップを流用しており、自転車が通行できない経路や交通ルール違反となる経路を案内しうる（縄野・間邊 2021 の**指摘**）。
- ただし、**実サービスの生成経路を実際に採点した実証データは存在しなかった。** 先行研究が示したのは指摘であって測定ではない。
- **本研究はこの空白を直接埋める。** Google Maps の出力経路を採点し、検出点の標識・道路状況をストリートビューで全点確認する。

### ⚠️ 言い方の注意

- 「Google Maps は法規を無視している」とは**言わない**。Google の内部アルゴリズムが法規を考慮しているかは非公開で証明不可能。言えるのは「Google のルートに法規違反エッジが N 件含まれていた」という観測事実だけ（`RESEARCH.md` 13.2節のフレーミング原則）。
- 「縄野・間邊が既存サービスの違反案内を実証した」とは**言わない**。同研究は指摘であり実測データはない。

## 3. 目的【必須】（1枚）

### 話す内容

1. **事前排除型の法規準拠ナビゲーションシステムを構築する。** 走行中に警告する（事後通知型）のではなく、ルート生成の段階で違反経路を排除する。
2. **自転車交通法規を類型化し、対応可能性を切り分ける。** 全ての法規が経路レベルで排除できるわけではない。何を経路で排除し、何を走行ガイダンスに委ね、何が現状のデータでは対応困難かを線引きし、その根拠を示す。
3. **既存サービスとの比較により評価する。** Google Maps のルートと本システムのルートを**同一の判定関数**で採点し、違反数と距離コストのトレードオフを実測する。

## 4. 先行研究【必須】（1枚）

### 話す内容

**(a) 縄野・間邊（2021）— 最も直接的な先行研究**

> Taichi Nawano and Tetsuya Manabe, "Route Calculation for Bicycle Navigation System Following Traffic Rules," *IEICE Transactions on Fundamentals*, E104-A(2), 366–370, 2021.

自動車用ノードマップに道路の左右を表すリンクを追加し、右側通行となるリンクの重みを無限大に設定する。さいたま市内57ポート間の2,930経路で比較。**査読付きのSpecial Section Letter である。**

| 観点 | 縄野・間邊（2021） | 本研究 |
|---|---|---|
| 対象法規 | 左側通行 | 一方通行（経路除外）＋二段階右折（案内） |
| 地図 | 出所を明記しない拡張ノードマップ | **OSM**。PBFとタグの時点を固定して明示 |
| 比較対象 | 自作のC/L/L+W | **外部サービス（Google Maps）** |
| 検証 | 2,930経路の机上シミュレーション＋アンケート | **検出点の全点をストリートビューで目視確認** |
| 誤差の扱い | 検出妥当性の現地検証なし | **タグ不備・分離way誤対応・候補僅差性を定量化** |

**(b) Loidl & Hochmair（2018）— 商用サービスとの差異**

35の自転車ルーティングポータルを調査し、**安全ルート（safest route）を明示的にそう銘打って提供するポータルは一つもなかった**（1件のみ賠償責任回避のため婉曲表現で提供）。ただしこれは**UI選択基準の調査**であり、ルートが実際に法規違反を含むかの検証ではない。

### ⚠️ 言い方の注意（発表でやりがちな誤り）

- **「事前排除型であること」を縄野・間邊に対する差別化軸にしない。** 同研究も重み∞で探索段階から除外しており、事前排除という発想は共通である。**事前排除は商用サービスに対する比較軸としてのみ使う。**
- **「先行研究は査読なし」と言わない。** 2021年に査読付きのLetter版が存在する。
- **Loidl & Hochmair を「法令遵守機能がないことの根拠」に使わない。** safest routeの明示提供状況の調査である。
- 縄野・間邊のアンケートは本文37名との記述に対し比率の分母が29に整合するという内的矛盾があるため、**比率を確定値として引用しない**。

### 差別化として言ってよいこと（4点）

1. **対象法規の範囲** — 一方通行（経路除外）＋二段階右折（案内）という二層の切り分け
2. **OSMという公開標準データ上での実装** — PBFのSHA-256とタグ時点を固定し再現可能にした
3. **外部サービスとの直接比較** — 同一判定関数でGoogle Mapsのルートを採点した
4. **検出結果の全点検証** — 検出点の標識・道路状況をストリートビューで全点確認し、誤検出の原因を分類した

## 5. システム構成【必須】（1枚）

### 話す内容

### 【図】全体アーキテクチャ図

```
ユーザ入力（住所・地名）
        ↓  Nominatim（ジオコーディング）
FastAPI バックエンド
   ├─ GraphHopper（Docker）        → ① 初期ルート生成
   ├─ Overpass API                 → ② OSMタグ一括取得
   └─ 法規チェックエンジン          → ③ 違反箇所を検出
        ↓ 一方通行違反あり
    GraphHopper（custom_model + areas） → ④ 当該区間を除外して再ルーティング
        ↓
React + Leaflet フロントエンド       → ⑤ 地図上に2本表示（最短／法規準拠）
```

- 判定は **OSMタグに基づくルールベース**。`oneway` が `yes/true/1/-1` で、かつ `oneway:bicycle=no` や `cycleway=opposite*` の自転車除外タグがない場合に、進行方向照合を経て違反とする。
- 違反エッジの除外は **GraphHopper の `custom_model` の `areas`** で行う。違反座標を中心とする約100m四方のポリゴンを priority `multiply_by: 0` でブロックし、再探索する。
- **二段階右折はリルートのトリガーにしない。** 経路は合法であり、走行手順を守れば違反にならないため、案内に委ねる。

### ⚠️ 質問されたら正確に答えること

「事前排除」の実装は**2パス構成**である。① 初期ルートを生成 → ② 判定 → ③ 違反があれば当該エリアをブロックして再生成。利用者に提示されるのは③の結果なので利用者から見れば事前排除だが、**内部では「生成→検出→再生成」である**。custom_model が最初から常時かかっているわけではない。

## 7. 評価方法【必須】（1枚）

### 話す内容

**評価指標（3つ）**

| # | 指標 | 定義 |
|---|---|---|
| ① | 一方通行違反件数 | ルート上で検出された oneway 違反エッジの絶対数 |
| ② | 距離オーバーヘッド | 法規準拠ルートと最短ルートの距離差（m および %） |
| ③ | 二段階右折検出数 | 右折地点で二段階右折義務ありと判定された数 |

**実験1：Google Maps との比較（15ペア）**

- 関東圏の15 O-Dペア。幹線道路中心5件／住宅街中心5件／混在型5件

- Google ルートは40m等間隔で379点をサンプリングして判定

**実験2：検出点の全点検証**

- 検出された点すべてについて、Google ストリートビュー画像で標識・道路状況を目視確認する
- 確認するのは、一方通行標識の有無、「自転車を除く」補助標識の有無、「車両進入禁止」標識の有無、対向車線との分離構造
- 撮影年月とOSMタグの最終更新日を併記して記録する

### ⚠️ 明記すべき既知の非対称（質問対策としても重要）

### 8-2. 検出点の全点検証（1枚）

**話す内容**

### 8-3. 3つの系統的限界（1枚）

**話す内容**

誤検出16点の原因を分類した結果、**3つの系統的な限界**が特定できた。これらは道路種別によって排他的に分かれる。

**【図】3つの限界の対比表**

| 項目 | 限界1（タグ不備） | 限界2（分離way誤対応） | 限界3（候補の僅差性） |

| 現象 | 現地の「自転車を除く」補助標識がOSMに反映されていない | 上下線が別wayの幹線道路で、座標から対向車線を誤選択する | rank1と次点wayの距離差が小さく、候補選択が不安定になる |

### 8-4. A群の年代分析と、回避のコスト・R1の測定状況（1枚）

このスライドは2つの内容を持つ。時間が厳しければ**A群の年代分析を口頭のみ**にし、回避のコストとR1の測定状況を図にする。

#### (a) A群の年代分析 —「タグ不備はいずれ直る」への回答

限界1に対しては「OSMのタグ不備はいずれコミュニティが修正するのだから恒久的な限界ではない」という反論が想定される。A群6点について**ストリートビュー画像の撮影年月**と**OSMタグの最終更新日**を突き合わせると、この反論に直接答えられる。

| 類型 | 該当 | 内容 |
|---|---|---|
| **放置型**（2点） | P09（way 325347768）・P17（way 142222817） | タグ最終更新が2016年のまま、8/1固定時点まで**約10年**（10.03年・9.66年）更新されていない。撮影年月はタグ更新の約8年後で、その時点でも補助標識が存在したことが画像で確認できる |
| **編集見落とし型**（3点） | P04（23690216）・P07（80835360）・P08（350353685） | 撮影年月がタグ更新より**前**。標識が存在すると画像で確認できる状態のまま、**その後にwayが編集されているのに除外タグが追加されていない**。とくにP08は `note=FixMe:Please adjust the position actively.` という能動的な修正依頼が付いていたが補われていない |
| 判定保留（1点） | P01（138533178） | 撮影年月がタグ更新より後だが差は約11か月。順序から結論を導けない |

**編集見落とし型のほうが強い反証である。** 放置型は「誰も触っていないから直らない」だが、編集見落とし型は「**触っていても直らない**」であり、編集回数や編集者数の増加では解消しない不備があることを意味する。

**⚠️ 必ず併記する限定：n=6 であり統計的な一般化はできない。割合（%）を書かない。** また、ストリートビュー画像の撮影年月は**その時点で標識が存在したことを示すのみ**で、その前後の状態は不明である。

**言い方（このまま話せる形）：**
