**予想される結果と、その扱い（実行前の見立て）**

`unknown` は 0 件に近くなると予想される。`check_oneway_violation` は `oneway`
タグの有無を決定的に判定するため、タグがあれば必ず判定に入るからである。
**0 件でも問題ない。** それは設計どおりに動いている証拠であり、
「タグベース判定は見逃さないが空振りする」という非対称性を示す結果になる
（Precision 側の A群・B群＝誤検出と対をなす）。数字を作りにいかず、
実際に出た値をそのまま記録すること。

`unknown` が複数出た場合は限界2（分離ウェイの誤マッチ・24.2節）・
限界3（候補の僅差性・24.3節）の別の現れ方である可能性があり、
スクリプトは各候補の `match_ambiguous` と最近傍候補の状況を D 節に併記する。

`short_segment` についても補足しておく。現行の `check_oneway_violation` では
短区間でも confidence が 0.7 に下がるだけで**検出自体は残る**ため、本来この理由で
未検出になることはない。**件数が 0 でない場合は判定経路の確認が必要。**

## E. タグ基準 Recall の暫定値

**人手判定前なので確定値は出せない。** 下記は上下の幅を示すためのもの。

記号: D = 同一実行で検出された `oneway` 違反 way 数、U = `unknown`、
S = `short_segment`、T = `tag_fetch_failed`。

| 仮定 | 計算式 | Recall |
|---|---|---:|
| 最良（`unknown` は全て正しい非検出） | D / (D + 0) | （未測定） |
| 最悪（`unknown` は全て真の見逃し） | D / (D + U) | （未測定） |
| 参考（要確認 U+S+T 件を全て見逃しと仮定） | D / (D + U + S + T) | （未測定） |

**この値の読み方（注意）：**

- 分子の D は「検出された件数」であり、**真陽性の件数ではない**。現地確認で
  偽陽性と判明した分だけ分子は下がる。R1 の Precision 側（現地確認済みの分類）を
  確定させてから改めて計算すること。
- 分母は **OSM に `oneway` タグがある way に限定**されている。「現地は一方通行だが
  タグがない」道（限界1・A群と同じ構造）は最初から母集団に入らないため、
  この Recall は現実基準の Recall の**上限側**に偏る。
- `bicycle_exempt` / `forward_travel` は「検出しないのが正しい」ケースなので、
  見逃しには数えていない（真陰性に相当する）。

## 付記：診断ロジックの出所

- 進行方向照合は `services/law_checker.py` の `_check_direction` を、ジオメトリの
  クリップは `services/route_analyzer.py` の `_trim_geometry` を**そのまま呼んでいる**
  （スクリプト側で再実装・近似していない）。
- way ごとの区間（`start_idx`〜`end_idx`）と travel_vector の作り方は `_analyze_v3` と
  同一。同じ way が複数区間に現れた場合に最初の区間のみを採用する規則も揃えてある。
- **方向情報は「なぜ検出されなかったか」の説明にのみ使い、マッチ候補の選択には
  使っていない**（循環論法の回避・RESEARCH.md 21.11節）。edge_id ベース判定では
  way_id を GraphHopper から直接受け取るため、そもそも最近傍マッチングが介在しない。
- 検出された違反の way_id は過去の CSV ではなく**同一実行のレスポンス `violations[]`**
  から取っている（OSM 更新で値が変わるため）。
- `fn_reason` の優先順は指示どおり 1〜5 の順に評価する。ただし
  **そのペアで `using_edge_ids=False`**（Overpass の by-ID 取得が失敗し、判定器が
  10点サンプリングにフォールバックした）場合だけは、1〜3 を評価する前に
  `tag_fetch_failed` を返す。この場合 way ごとの照合そのものが行われておらず、
  「順走だったから検出されなかった」と書くのは事実に反するため。
