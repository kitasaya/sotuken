# 調査報告：oneway違反7件（コードB）の誤マッチ原因調査

**調査日**: 2026-07-24
**対象**: 現地確認でコードB（左側通行していれば合法・システムが逆方向の道を選択している疑い）
に分類された7件（way_id: 22961575, 741785139, 667962675, 474601303, 271979254,
1429406683, 263457845）
**目的**: B群の原因が `check_oneway_violation` の判定ロジックではなく、
`external_route_scorer.py` の polyline→way マッチング処理（座標ベースの最近傍探索）に
あるという仮説を、事実に基づいて確定する。

**本調査では `ground_truth.csv`・`google_comparison.csv`・`google_routes_input.csv` および
`external_route_scorer.py`・`law_checker.py` 等の本体コードは一切変更していない。**
調査用スクリプトは `/tmp` 配下に作成し、結果のみを本ファイルに記録した。

---

## 手法の概要

前回調査（`investigation_138533178.md`）と同じ再現手順（`google_routes_input.csv` の
polyline に対して `external_route_scorer.py` の判定ロジックをそのまま呼び出す）で
18件の oneway 違反を再現した。件数は `google_comparison.csv` の
`google_oneway_violation_count` 列（15ペア合計18件）と完全一致し、再現性を確認済み。

各違反点について:
- 違反点の直前・直後の polyline 座標、マッチした way の geometry・ノードID列を取得（Step 1）
- polyline の進行方向ベクトルとマッチした way の方向ベクトルの角度差を算出（Step 2）
- 違反点から半径30m以内の全 highway way を Overpass から取得し、同名・逆方向の
  `oneway=yes` way（分離ウェイ候補）の有無と距離を調査（Step 3, 4）
- D群（1件）については独立に別分析を実施（Step 5）

## 誤マッチの発生メカニズム（根本原因の特定）

Step 3 で判明した「分離ウェイの方が真の距離（点から線分への垂線距離）で近いのに、
マッチしたwayは遠い」という逆転現象がなぜ起きるかを、実際にシステムが使っている
マッチング方式（`services/overpass.py` の `get_bulk_way_data` / 本調査の
`get_bulk_way_data_with_id`）で検証した。

このマッチング処理は、Overpass から取得した各wayについて **「wayを構成するノード
（頂点）のうち最も近いものまでの距離」** で最近傍wayを決定している（`overpass.py` の
`get_bulk_way_data` 内、`for node in geom_nodes: d = (node["lat"]-lat)**2 + ...`
の箇所）。これは「点から線分（セグメント）への垂線距離」とは異なる。

4件のサンプルについて、両方の距離指標を直接比較した:

| label | matchedway<br>ノード最近傍距離 | matchedway<br>垂線距離（真の距離） | 分離ウェイ<br>ノード最近傍距離 | 分離ウェイ<br>垂線距離（真の距離） |
|---|---|---|---|---|
| 東京→渋谷(外苑東通り) | **8.54m** | 7.66m | 13.96m | **0.8m** |
| 品川→東京(中央通り) | **10.85m** | 9.43m | 15.34m | **0.74m** |
| 川崎→武蔵小杉(南武沿線道路) | **22.02m** | 10.05m | 29.15m | **1.23m** |
| 千葉→幕張本郷(国道126号) | **10.3m** | 9.37m | 31.09m | **3.35m** |

**4件全てで同一のパターンが確認された：ノード最近傍距離で比較するとマッチしたway
（システムが実際に選んだway）の方が近いが、垂線距離（実際に道路が通っている位置までの
真の距離）で比較すると分離ウェイ（本来マッチすべきだった順走方向のway）の方が明確に
近い。**

つまり原因は判定ロジック（`check_oneway_violation`）ではなく、**`get_bulk_way_data` /
`get_bulk_way_data_with_id` の最近傍way選択が「点から各wayのノードまでの距離」を
基準にしており、「点から各wayの線分（セグメント）までの距離」を基準にしていない**
ことにある。分離ウェイ（幹線道路の対向車線）はOSM上でノード間隔が疎な区間があると、
そのwayの実際の線（道路そのもの）は近くを通っていても、たまたま近くにノードが
無いために「遠い」と判定され、代わりにノード密度の高い反対車線のwayが選ばれてしまう。

## 結論

**仮説は成立した（B群7件中6件／8点中6点）。** 原因は `check_oneway_violation` の
判定ロジックではなく、`services/overpass.py` の `get_bulk_way_data` /
`get_bulk_way_data_with_id` における最近傍way選択が「点から各wayの**ノード**までの
距離」を基準にしており、「点から各wayの**線分（セグメント）**までの距離」を基準に
していないことにある。

判定基準表に照らすと:

> 分離ウェイあり・距離差小（B群） / 分離ウェイなし（C群）→ **仮説成立
> （マッチング精度の問題）**

この構図がB群8点中6点・C群3点中0点という明確なコントラストで確認された。うち4点
（271979254・667962675・263457845・22961575）は、ノード最近傍距離と垂線距離を直接
比較することで、「ノード密度の疎な正しいway」より「ノード密度の高い誤ったway
（反対車線）」が選ばれるという発生メカニズムそのものを実証した。

**部分的成立・保留とする2点:**

- **品川→東京 741785139**：分離ウェイ（同名・逆方向）は見つからなかったが、
  順走方向にほぼ平行な別道路（旧海岸通り、5.36m先）が存在した。マッチしたwayは
  `highway=tertiary_link`（連絡路/ランプ）で `name` タグを持たないため、
  「同名の分離ウェイ」という基準には合致しないが、「本線に近接する無名の短いlink way
  が誤って選ばれた」という点でB群の仮説（マッチング精度の問題）と同系統の
  サブパターンと考えられる。断定はしない。
- **立川→国分寺 1429406683**：分離ウェイ候補（立川南通り逆方向、5.49m）は存在するが、
  マッチしたway自体の方が垂線距離で近い（1.4m）。ノード距離/垂線距離の逆転現象は
  この点では確認されなかった。マッチング処理自体に誤りがあったとは断定できない
  （Google polylineの座標が本来中央分離帯寄りを通っていた可能性等、他の要因も
  考えられるが、本調査のデータからは特定できない）。

**D群（1件）は本仮説とは別要因であり、断定できない。** 分離ウェイ・順走候補いずれも
半径30m以内に存在せず、マッチング精度の問題という説明は当てはまらない。追加で
必要な情報は現地の立体構造（高架・側道等）の確認である。

**A群（6件）は仮説の対照として、分離ウェイが1件も存在しないことを確認した。**
A群のマッチしたwayはいずれも `name` タグを持たない生活道路であり、構造的に
「分離ウェイの取り違え」が起こり得ない（そもそも上下線が分離マッピングされていない）
道路である。これはA群の原因が「OSMデータ不備（自転車除外タグの欠如）」であり
B群の「マッチング精度の問題」とは独立した別要因であるという分類と整合する。
